# Alice Registry Layer

The Alice registry layer is the metadata backbone for county-aware land research.

It does three jobs:

1. Provides a canonical nationwide county index so every U.S. county or county-equivalent has a stable lookup path.
2. Stores curated county coverage entries for counties where Alice has better local source knowledge.
3. Stores source descriptors that future parcel resolution, source planning, and research orchestration can use before live adapters exist.

This layer is intentionally simple. JSON files are the system of record. Small Python utilities load, validate, and resolve the effective registry view.

## Directory Layout

```text
registry/
  us_counties.json
  county_overrides/
    <STATE_CODE>/<COUNTY_FIPS>.json
  sources/
    federal/*.json
    state/*.json
    county/*.json
    local/*.json
    listing_platform/*.json
```

## Nationwide County Backbone

`us_counties.json` is the canonical U.S. county index for Alice.

Maintenance source:

1. U.S. Census Bureau national county code table:
   - `https://www2.census.gov/geo/docs/reference/codes2020/national_county2020.txt`
2. U.S. Census Bureau state code table:
   - `https://www2.census.gov/geo/docs/reference/state.txt`

The file is generated by `scripts/build_us_counties_index.py`. The generated index includes counties and county-equivalents, along with a normalized `county_equivalent_type` and retained Census metadata such as class code and functional status.

If Census code tables change materially, regenerate the file rather than hand-editing thousands of rows.

## County Fallback vs Curated Override

Alice must support every county even when local research quality is uneven.

### Fallback entry

If a county has no curated override, Alice generates a valid minimal coverage entry from the county index.

Fallback behavior is intentionally conservative:

1. `coverage_tier = minimal`
2. Local capabilities default to weak or unavailable
3. National baseline sources remain attached
4. `known_limitations` states that the county is not yet curated
5. `last_verified_at = null`

This means Alice never has to "skip" a county just because local curation is missing.

### Curated override

Curated counties are stored as full replacement JSON rows under `county_overrides/<STATE_CODE>/<COUNTY_FIPS>.json`.

Chosen strategy:

1. No partial patching
2. No merge-by-field logic
3. Effective county entry = curated override if present, otherwise generated fallback

Full replacement is easier to reason about, easier to validate, and easier to review in git.

## Source Descriptor Organization

Source descriptors are stored one file per source and validate against `schemas/source_descriptor.schema.json`.

Current category layout:

1. `sources/federal/`
   - national baseline sources such as flood, wetlands, soils, elevation, broadband, and environmental screening
2. `sources/state/`
   - statewide sources that meaningfully improve parcel identity or infrastructure context
3. `sources/county/`
   - county or county-scoped sources such as parcel search, assessor pages, GIS, and local planning references
4. `sources/local/`
   - city or municipal planning sources when county-level land diligence depends on city-level context
5. `sources/listing_platform/`
   - listing platforms used for listing context and directional market-planning, never as authoritative substitutes for county or state records

Source descriptors should stay realistic and narrow. It is better to register a smaller set of authoritative sources than to add dozens of speculative stubs.

## Adding a County

To add county support:

1. Confirm the county exists in `us_counties.json`.
2. Decide whether the county still belongs on fallback or needs a curated override.
3. Add any new authoritative source descriptors first.
4. Create a full replacement county override JSON if curated coverage is warranted.
5. Run `scripts/validate_registry.py`.

## Adding a Source

When adding a new source descriptor:

1. Prefer authoritative public sources over aggregators.
2. Put the file in the directory matching its source category.
3. Scope `geography_scope` honestly.
4. Use the narrowest realistic `interface_type`.
5. Set `access_mode` explicitly so Alice can distinguish machine endpoints from landing pages and viewers.
6. Keep capability tags explicit and limited to what the source actually supports.
7. Set `status` conservatively if the source is unstable or requires manual handling.

## Interface Type vs Access Mode

Step 10 kept `interface_type`, but the stabilization patch adds `access_mode` because evaluators need to know whether a source is actually machine-addressable today.

Use them differently:

1. `interface_type`
   - what technical interface family the source belongs to
   - examples: `formal_api`, `gis_service`, `downloadable_dataset`, `web_only`
2. `access_mode`
   - how Alice is expected to touch the source at planning and retrieval time
   - examples:
     - `machine_endpoint`: direct machine query or service endpoint
     - `landing_page`: page access or download entry point, not a direct machine query
     - `viewer`: interactive map or viewer surface
     - `mixed`: Alice uses both a human-facing page and a derived machine endpoint for the same source family

Examples:

1. `federal_usgs_3dep_elevation`
   - `interface_type = gis_service`
   - `access_mode = machine_endpoint`
2. `federal_fema_nfhl`
   - `interface_type = web_only`
   - `access_mode = mixed`
   - because the descriptor is anchored to the NFHL program page while Step 6 executes a derived ArcGIS query endpoint
3. `county_ca_kern_interactive_mapping`
   - `interface_type = web_only`
   - `access_mode = viewer`
4. `listing_platform_landwatch`
   - `interface_type = web_only`
   - `access_mode = landing_page`

## Operational Meaning of Coverage Tier

Coverage tier is a county-source-environment statement, not a confidence score.

1. `full`
   - Alice has strong county or city-local parcel identity plus meaningful planning/zoning/tax context and national baseline overlays.
2. `partial`
   - Alice has meaningful local context, but one or more major diligence surfaces remain thin or inconsistent.
3. `minimal`
   - Alice can still produce a valid county path using fallback logic and baseline sources, but local diligence is weak or unverified.

Registry validation now checks this mechanically from county capability fields:

1. `full`
   - requires baseline environmental footing
   - requires `parcel_identity = full`
   - requires tax-roll footing of at least `partial`
   - requires zoning footing of at least `partial`
   - requires infrastructure footing (`utilities` or `transmission`) of at least `partial`
2. `partial`
   - requires baseline environmental footing
   - requires identity footing (`parcel_identity` or `tax_roll`) of at least `partial`
   - requires either planning footing (`zoning` or `planning_docs`) or infrastructure footing
3. `minimal`
   - everything else, including fallback counties where only baseline overlays are attached

`broadband` alone does not upgrade a county from `minimal` to `partial`.

Coverage tier should not be used as a proxy for confidence or completeness. Those are report-level outputs, not registry-level coverage labels.

## What This Step Does Not Solve Yet

This registry layer does not implement:

1. live HTTP fetchers
2. GIS query clients
3. parcel resolution
4. source parsing
5. recommendation ranking
6. memo synthesis or report rendering
7. automatic source discovery and freshness scoring

Those come later. This step only makes the registry backbone real, testable, and usable.
